# Phase 2 operations: blog, indexing, invoices

## Deployment boundary

The public website, including `blog.html`, remains on GitHub Pages. Blog posts, images, the post API, and the post sitemap live on `api.pawpad.in`. Publishing a post in Admin updates the API immediately and requires no Git push. Changes to the blog layout, navigation, static page SEO tags, or invoice code require deploying this repository and the matching `api/` files. `experience.html` and its CMS editor remain available by direct URL, but Experience is not in site navigation or the main sitemap.

Deploy the GitHub Pages files and `api/` changes together. The API schema updater creates the new tables on its next request. Keep `api/config.php` private; do not commit it. The bundled Dompdf release under `api/lib/dompdf/` is needed to generate invoice PDFs. Ensure the PHP host has the extensions required by Dompdf (including mbstring and DOM) and a writable `api/private/invoices/` folder. Verify that `https://api.pawpad.in/private/` returns 403 before issuing any invoice. Back up **both** MySQL and `api/private/invoices/`; the Website Content JSON export does not include invoices or blog posts.

## Blog publishing

Owner or Administrator: Admin → Blog Posts → New article. Write the article in sections, upload pictures through the media manager, and add descriptive alt text. The keyword button suggests phrases from the article text; review and edit them. Save a private draft, then publish. A published post is available at `https://pawpad.in/blog.html?post=<slug>`. Published slugs cannot be changed, preserving links. Unpublishing removes the post from the public API and live sitemap.

The first API schema update to version 16 publishes three sample articles from `api/lib/sample-blog-posts.json`, using images already in the public `assets/img/pawpad/` folder. The seed runs once and skips an existing slug, so later Admin edits and unpublishing are preserved. Deploy the API update and matching GitHub Pages files together; a local code change alone does not put these articles on the live site.

For local static hosting (`localhost` or `127.0.0.1`), the Blog page previews those same three sample articles directly from the JSON file when the blog API is unavailable. A successful API response replaces the local preview, including an empty published list; a 404 for an article also takes precedence. On `https://sntharun.github.io/PawPad-New/`, the sample articles remain visible as staging content and published API posts are added or replace matching slugs. The live `pawpad.in` domain always uses the API as the source of truth.

The API exposes only published posts through `list_blog_posts` and `get_blog_post`; admin actions require Owner or Administrator. The dynamic sitemap is `https://api.pawpad.in/index.php?action=blog_sitemap`, referenced in the main `robots.txt`. The public `get_content` response does not carry articles.

## Search indexing checklist

1. Deploy the public site and matching API, then publish a complete test article with a valid cover image and alt text.
2. Confirm the article renders at its stable URL on desktop and mobile, and that its canonical URL, description, Open Graph tags, and `BlogPosting` JSON-LD match the article.
3. Confirm the API sitemap lists only published URLs. Verify both `https://pawpad.in/sitemap.xml` and the API sitemap in Google Search Console for the domain property, then submit them.
4. Use Search Console’s **Test Live URL** on the article and inspect its rendered HTML. The post is loaded by JavaScript, so this live-render check matters. A sitemap or indexing request does not guarantee indexing.

The six course detail pages now have static descriptions and canonical URLs. Application forms, the success page, the generic course page, and Admin are marked `noindex`. Static page metadata changes still require deployment. `experience.html` remains directly accessible with its existing canonical tag; removing it from navigation and sitemap alone does not remove it from search results.

## Invoice workflow

1. Owner/Administrator enters the legal issuer, registered address and state name/code, GST status and GSTIN where applicable, whether GST e-invoicing applies to the issuer, numbering prefix, authorized signatory and private signature image, and the accountant-approved service codes and tax rates for course, grooming, boarding, consulting, and other services. If GST e-invoicing applies, this API blocks B2B invoice and note issuance because it does not register documents with an Invoice Registration Portal (IRP). Do not mark it “does not apply” merely to bypass the block.
2. Owner/Administrator records the accountant’s name and approval reference, then approves the settings. The separate domestic credit/debit note checkbox must remain off until the accountant has approved adjustment treatment and the CN/DN document series. Any later settings edit locks invoice and note issuance until reapproval. **Do not infer tax rates or invoice details from website prices.** This implementation treats entered unit prices as tax-inclusive and splits GST into CGST/SGST or IGST based on the customer and issuer state codes; the accountant must approve that treatment for the actual services.
3. Staff creates a draft sale with billing and delivery addresses, state name/code, line items, and the relevant course payments, completed grooming closings, or boarding request. A boarding request is context only: it contains no verified payment, so record its payment separately with amount, date, mode, and a receipt or transaction reference. The same manual payment path covers consulting and other services. Staff verifies the customer, final amount, and that reverse charge does not apply. A sale requiring reverse charge, exports, or other special treatment must wait for an accountant-approved extension.
4. Owner, Administrator, or Manager issues the sale when verified payments equal the invoice total exactly. A course application or grooming order can belong to only one sale; manual payment mode/reference pairs cannot be reused. Issuance allocates a number by financial year, stores a fixed PDF and snapshot, and attempts email from `info@` if the customer email is available. Email failure leaves the invoice issued; retry from the register. Only Owner/Administrator can change a delivery email after issuance, and the change is logged.
5. Course payment and grooming closing views display linked invoice and issued note numbers. An issued invoice prevents deletion of its course payment, recording another course payment against that application, editing any grooming closing in the same order, or cancelling its linked boarding request. Before issuance, every recorded payment in a linked course application and every completed paid grooming closing in the same order must be linked to that sale. Later price changes and their additional payments belong in the invoice register, not as unlinked payments in the original source record. Owner/Administrator can log nonfinancial corrections without overwriting the issued PDF.
6. For a domestic refund or price decrease, Owner/Administrator drafts a **credit note** against one or more original invoice lines and enters the gross amount to reduce on each line. For a price increase, use a **debit note**. Notes cannot be issued until the accountant has separately approved domestic adjustments and the CN/DN numbering series in Billing settings; each note also requires a saved accountant review reference. Issued notes get immutable numbered PDFs and email delivery with retry. Credits cannot exceed the original line amount across all issued credit notes. The register shows the original amount, net amount after notes, payments, and remaining balance. A credit note is separate from actually returning money: after a verified payout, record the amount/date/mode/reference against the issued credit note. The refund mode must match a payment method on the original invoice, per the website refund policy. Check the service cancellation and non-refundable deposit policy before approval. Likewise record a verified additional payment against an issued debit note. The register limits each payout/collection to the corresponding note total. Keep bank/payment-provider evidence with finance records; the Admin record is entered by staff and does not send money or charge a card.
7. The accountant must review timing and tax-return treatment of every financial note, especially after a return has been filed. The software does not submit GST returns or change invoices already reported to the government. Nonfinancial identity/address corrections still need accountant review if the original statutory document is wrong.

The website checkout does not collect online payment; HubSpot and Web3Forms currently handle enquiries/notifications, not the authoritative sale ledger. Invoices therefore link to the server’s payment and closing records rather than making HubSpot or Web3Forms a second source of truth.

## Local verification and remaining production checks

Run `npm run build` and `npm test` locally. The frontend blog can be tested with a mocked API. A real PHP/MySQL integration test is still required on a staging copy of the API and database: migration, role permissions, grouped payment matching, concurrent invoice/note numbering, credit limits across multiple notes, tax rounding, partial refunds/collections, PDF totals and file protection, email failure/retry, and the Search Console live render. Do not enable invoice or note issuance until the accountant-approved details and production storage checks above are complete.
